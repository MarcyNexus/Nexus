# `supabase/` — Backend Project Config

← [back to overview](./00-overview.md)

## Why Supabase, and why this folder exists

Supabase is the backend for both apps: it provides a real Postgres database, user
authentication, file storage, realtime subscriptions, and serverless Edge Functions
— all reachable from either app through the `supabase` client each one constructs
via `@marcy-nexus/shared`. See [00-overview.md](./00-overview.md) for the
Firebase-vs-Supabase comparison that led here.

Crucially, **this folder does not contain your actual database or data** — that
lives on Supabase's servers, in the hosted project referenced by
`SUPABASE_URL=https://boqdteaubdbbjtywniua.supabase.co` in the root `.env` file.
What's in this folder is the **Supabase CLI's local project configuration** —
created by running `npx supabase init` — which exists so that:

- Local development can spin up a matching Postgres/Auth/Storage stack in Docker
  (`npx supabase start`) instead of every code change hitting the live hosted
  project directly.
- Database schema changes can be tracked as versioned migration files and applied
  consistently to both the local stack and the real hosted project, rather than
  being made ad hoc through the dashboard with no history.
- The CLI has a single source of truth for local port numbers, feature toggles, and
  auth settings to mirror against the hosted project's real settings.

None of that local Docker stack has been started yet — this is just the
configuration scaffold. Nothing here talks to your real project until you run
`npx supabase link --project-ref boqdteaubdbbjtywniua` (see the root
[README.md](../README.md) for the full command sequence).

## File-by-file

### `config.toml`
The CLI's main configuration file, organized into sections. The generated defaults
are broad — most of it is inert until you opt into that feature — but worth knowing
what's here:

- **`project_id`** — set to `"marcy-nexus"` (defaults to the folder name at
  `supabase init` time). Distinguishes this project's local Docker containers from
  any other Supabase project you might run locally on the same machine.
- **`[api]`** — configuration for the local REST/GraphQL API: which Postgres schemas
  are exposed as endpoints (`public`, `graphql_public`), the local port (`54321`),
  and a row-count safety cap (`max_rows = 1000`) to stop one query from returning an
  unbounded payload.
- **`[db]`** and **`[db.pooler]`** / **`[db.migrations]`** / **`[db.seed]`** — local
  Postgres settings, connection pooling behavior, where migration files are expected
  (`supabase/migrations/`, not created yet — no schema exists yet), and optional
  seed-data configuration for resetting the local database to a known state.
- **`[realtime]`** — local config for Supabase's websocket-based realtime
  subscription feature (e.g. listening for live row changes in a table).
- **`[studio]`** — the local web dashboard (Supabase Studio) that
  `npx supabase start` serves, for browsing/editing the local database visually.
- **`[storage]`** and its subsections — local file storage (S3-compatible protocol),
  used for things like user-uploaded images or documents.
- **`[auth]`** and its many subsections (`rate_limit`, `email`, `sms`, `mfa`,
  `external.apple`, `third_party.firebase`/`auth0`/`aws_cognito`/`clerk`, etc.) —
  every authentication method Supabase supports, all disabled/unconfigured by
  default. This is where you'd later enable email/password sign-in, social logins,
  or MFA once auth is actually built.
- **`[edge_runtime]`** — local execution environment for Supabase Edge Functions
  (the serverless functions included free on Supabase's plan, mentioned in the
  Firebase-vs-Supabase comparison).
- **`[analytics]`** and **`[experimental]`** — opt-in local analytics logging and
  CLI features still in preview (e.g. `pgdelta`, a schema-diffing approach still
  being finalized by Supabase).

None of these need to be touched yet — they only matter once local development via
`supabase start` actually begins.

### `.gitignore`
Auto-generated by `supabase init`, scoped to this folder specifically (ignoring
things like `.branches` and `.temp`, which the CLI creates locally and which
shouldn't be committed alongside the actual migration/config files that *should* be
tracked).

## How this connects to the root `.env` file

The root-level `marcy-nexus/.env` file (see
["A note on secrets" in 00-overview.md](./00-overview.md#a-note-on-secrets-and-where-each-key-lives))
holds:

- `SUPABASE_URL` — this project's real hosted API URL.
- `SUPABASE_SECRET_KEY` — the `sb_secret_...` key, which has full server-side
  privileges (bypasses Row Level Security). This is the key you'd use from a trusted
  server-side context only — for example, a future admin script, a CLI migration
  tool, or a server-side-only Next.js Route Handler that needs elevated access. It
  must never be read into `NEXT_PUBLIC_*`/`EXPO_PUBLIC_*` variables inside either
  app, since those get bundled into client-side code that ships to every browser or
  phone running the app.

Still needed, and intentionally **not** in the root `.env`: the **publishable** key
(`sb_publishable_...`), which is the client-safe counterpart. That one goes into:

- `apps/web/.env.local` → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `apps/mobile/.env` → `EXPO_PUBLIC_SUPABASE_ANON_KEY`

Both alongside `NEXT_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_URL`, matching the
same project URL.
